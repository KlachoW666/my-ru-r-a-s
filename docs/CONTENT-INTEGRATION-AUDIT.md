API и сохранение. В браузере доступен только экран Passkey; вход не выполнен.
На боевой сервер изменения не выкладывались.

**Блокер данных:** текущая `case_items` пуста. У всех пяти кейсов нет состава.

Для восстановления нужны исходный CSV/JSON или другая резервная копия со связями
и шансами. Из общего каталога нельзя определить, какие призы были выбраны.

## Причины

- Фронт предметов отправляет `name`, старый API читал `search`.
- `upgraderEnabled`, `ids[]` и `type_color` не применялись.
- Общий компонент списка считает страницы через `pagination.total`, а сервер
  возвращал только верхнеуровневый `total`.
- Расписание серий читалось как `row.series.id`, но API возвращал плоские строки.
- Кнопка экспорта кейсов сама собирает CSV из `response.data`; сервер отдавал CSV
  вместо массива кейсов с составом.
- Форма создания из каталога отправляет `items[].catalogItemId`; обработчик
  ожидал один `itemId` и терял весь состав.
- Форма кейса отправляла только ID, без шансов. Её дополнительное сохранение
  через отсутствующий решатель RTP не завершалось.
- DELETE кейса физически удалял состав, хотя кнопка называлась «Деактивировать».
- Сайт выбирал все неархивные кейсы, игнорируя `isActive`, а кейсы выключенной
  серии переносил в «Популярные». Открытие также не проверяло статус.
- Страницы отправляются как `{type, content: object}`. Старый обработчик вставлял
  новую строку без сериализации JSON при каждом сохранении.

## Реализация

Основной модуль: `admin.titanrust.ru/server/contentRoutes.js`.
Он регистрируется **до** старых маршрутов контента в `server.js` админки.
Старые обработчики ещё существуют; менять нижний дубликат бессмысленно.

Многозаписные изменения выполняются на отдельном SQLite-соединении в транзакции.
Ошибки не должны оставлять половину состава или затрагивать параллельные операции
кошелька на общем соединении. Импорт использует savepoint для каждого кейса.

Схема дополняется при первом запросе к модулю:

- `content_page_types(type)`;
- `content_page_meta(page_id, version, locale, updated_by, updated_at)`;
- недостающие поля `cases` (`sortOrder`, `isBlogger`, `exclusiveTo`, `seriesId`,
  `status`, `isActive`, `archived`, `category` и поля оформления);
- `case_items.chance`, `ticketRangeFrom`, `ticketRangeTo`;
- недостающие поля `items`, включая `upgraderEnabled`, `delisted`,
  `admin_disabled`, `rarity_color`, `classid`.

Миграция завершается до открытия транзакции сохранения. Это устраняет боевой
сценарий, где форма была новее `database.sqlite` и сервер отвечал 500 с
`no such column` или `table cases has no column named ...`.

`admin_disabled` отделяет решение администратора от отсутствия предмета на рынке.
Синхронизация может сбросить `delisted`, но не должна отменять административное
отключение. Используемый в кейсах предмет нельзя отключить: API отвечает 409.

Импорт CSV поддерживает создание новых кейсов. Не перезаписывает общие цены и
редкости предметов: несовпадения возвращаются как ошибки строк. Автоматическая
архивация существующей серии не реализована и отвечает 501.

- `CaseFormModal.vue_vue_type_script_setup_true_lang-84FjkQIS.js`: отправляется
  состав с шансами и диапазонами; удалён второй вызов отсутствующего решателя

- `PagesListPage-DAmzDkL1.js`: неправильный JSON вызывает ошибку, а не сохраняет
  пустой объект.

Исходников Vue нет. При новой сборке эти изменения затрутся — перенести их в
исходные компоненты, когда они появятся. Не добавлять `?v=` к entry-скрипту.

## Неподключённые действия

501 — это **отсутствие реализации**, а не готовая кнопка. Такой ответ заменяет
фиктивный успех для тиражей и жизненного цикла лимитированных серий, мониторинга,
аудита, пакетного RTP и auto-derive. GET базового `rtp_96` возвращает объект с
`items`; независимых распределений по другим тирам в игровом движке нет.

Оставшиеся риски: загрузчик `/media/upload` требует отдельной проверки типов
файлов и допустимых папок; `/media/reprocess` не реализован. Обычные поля серии
сохраняются, но жизненный цикл ограниченной серии нельзя считать подключённым.

## Проверки

```powershell
node --test tests/*.test.js
```

На момент обновления: полный набор содержит 302 проходящих теста. Контракт
контента отдельно проверяет создание и изменение кейса на старой схеме БД.
Первые тесты контента падали на прежних обработчиках. Новые сценарии также
проверяли ошибки до соответствующих исправлений; дополнительные граничные
проверки покрывают существующую валидацию.

Тесты используют временную SQLite, не реальные строки пользователей/кейсов.
Проверка HTTP на локальном порту 8080: списки кейсов, предметов, каталога, серий,
расписание, страницы, типы, баннеры — 200 без `catchAll`. Это проверка API, не E2E.

Для браузерной приёмки нужен доступ к тестовой админке с Passkey и корректными
`ADMIN_RP_ID` / `ADMIN_ORIGINS`. В текущем локальном запуске зарегистрировано
0 ключей, а `ADMIN_REQUIRE_AUTH=0`; публиковать такую конфигурацию нельзя.
