# Каталог предметов Steam

Реализация: [services/steamCatalog.js](../services/steamCatalog.js). Запускается автоматически вместе с `server.js`, отключается через `STEAM_CATALOG_SYNC=0`.

## Что проверено живыми запросами

Всё ниже — результат реальных обращений к Steam 2026-08-23, а не предположения. Это важно, потому что документация Steam на эти эндпоинты отсутствует, а в интернете гуляют устаревшие сведения.

| `count=100` / `50` / `20` | Steam возвращает **10** и `pagesize: 10`. И с `norender=1`, и без него |
| `currency=5` | игнорируется, цена приходит как `"$7.22"` |

| заголовок `Accept-Language: ru` | игнорируется |

| `asset_description.tags` | **поля нет** — официальной редкости у предметов Rust не отдаётся |
| `asset_description.name_color` | есть, ровно 4 значения на 160 предметах, 0 ошибок |
| `sort_column=name&sort_dir=asc` | работает, порядок стабильный — страницы не пересекаются |

## Почему не «раз в 30 секунд»

Просьба была обновлять все 5430 предметов каждые 30 секунд. Это невозможно, и вот арифметика:

```
5430 предметов ÷ 10 за запрос = 543 запроса на полный круг
543 запроса ÷ 30 секунд       = 1086 запросов в минуту
```

Безопасный анонимный темп для market-эндпоинтов — примерно **20 запросов в минуту**. Превышение даёт HTTP 429 и временную блокировку IP, которая при повторах растёт. 1086 req/min — это пятидесятикратное превышение: сервер получил бы бан в первую же минуту и каталог перестал бы обновляться вообще.

**Что сделано вместо этого — и почему это даёт нужный результат:**

| Слой | Частота | Как |
|---|---|---|
| Сайт → API | мгновенно | читает SQLite, в Steam не ходит **никогда** |
| API → отдача | **30 секунд** | кэш в памяти, TTL 30 с |
| Воркер → Steam | ~27 минут на круг | 543 запроса с интервалом 3 с, непрерывно по кругу |

То есть пользователь видит обновление данных с задержкой не больше 30 секунд — ровно то, что требовалось. А цена конкретного предмета на Steam за 30 секунд всё равно не меняется: торговая площадка пересчитывает их куда медленнее.

Ускорить можно только уменьшением `STEAM_REQUEST_INTERVAL_MS`, и это прямо повышает риск бана. 3000 мс — проверенный безопасный минимум.

## Редкость

Официального поля редкости Steam для Rust не отдаёт (`tags` отсутствует). Единственный источник — `asset_description.name_color`. Скан 160 предметов по всему каталогу:

| Цвет Steam | Доля | Цена (USD) | Тир Rust | Тир сайта |
|---|---|---|---|---|
| `#dddddd` | 1.3% | $0.15–$0.20 | Common | `REGULAR` `#756767` |
| `#a7ec2e` | 31.3% | $0.74–$23.51 | Uncommon | `UNUSUAL` `#4076ff` |
| `#35a3f1` | 32.5% | $0.66–$9.35 | Rare | `RARE` `#65dc04` |
| `#f15840` | 35.0% | $0.83–$29.28 | Very Rare | `VIOLET` `#a33ee2` |
| — | — | ≥ `GOLD_MIN_PRICE_RUB` | — | `GOLD` `#ffc43b` |

**Соответствие построено по рангу, а не по похожести цвета.** У Rust порядок Common < Uncommon < Rare < Very Rare, у палитры сайта — REGULAR < UNUSUAL < RARE < VIOLET < GOLD, и цвета в этих двух шкалах идут в разном порядке (у Steam зелёный ниже синего, у сайта наоборот). Редкость — это ранжирование, поэтому сохраняется именно порядок; исходный цвет Steam при этом лежит в колонке `rarity_color`.

Тир `GOLD` Steam не выделяет вообще, иначе верхний тир сайта остался бы пустым. Поэтому предметы дороже `GOLD_MIN_PRICE_RUB` (по умолчанию 5000 ₽) поднимаются в него. Порог настраивается, `0` отключает поведение.

### Почему нельзя по цене

Старый `getRarity()` в [steamSync.js](../services/steamSync.js) определял редкость по цене (`≥8000 → COVERT` и т.д.). Скан показывает, что диапазоны цен разных цветов **перекрываются почти полностью**: зелёный `#a7ec2e` встречается по $0.74 и по $23.51, синий `#35a3f1` — по $0.66 и по $9.35. Цена и редкость в Rust не связаны, так что этот способ давал неверный тир.

## Цены

Steam отдаёт только USD (`sell_price` в центах). Конвертация делается здесь:

```
цена₽ = (sell_price / 100) × USD_RUB_RATE × PRICE_MULTIPLIER
```

Курс подтягивается автоматически раз в 6 часов, `USD_RUB_RATE` — запасное значение. Исходная цена в центах сохраняется в `price_usd_cents`, поэтому пересчитать весь каталог под новый курс можно без обращения к Steam.

`PRICE_MULTIPLIER` — наценка магазина к рыночной цене (`1` = без наценки).

> **Была ошибка в старом коде:** `steamSync.js` брал `sell_price / 100` и записывал результат как рубли. То есть предмет за $7.22 попадал в базу как «7 ₽» — расхождение примерно в 83 раза. Строки, пришедшие оттуда, определяются по `price_usd_cents IS NULL` и перезаписываются по мере обхода.

## Как работает воркер

```
startWorker()
  └─ бесконечный цикл
       ├─ runSweep()                     полный круг по каталогу
       │    ├─ offset берётся из sync_state.catalog_offset  (возобновление после рестарта)
       │    ├─ страница = 10 предметов, sort_column=name (стабильный порядок)
       │    ├─ upsert пачкой в транзакции по market_hash_name
       │    ├─ HTTP 429/503 → экспоненциальная пауза до 15 мин, offset НЕ сдвигается
       │    └─ конец круга → offset=0, непойманные предметы → delisted=1
       └─ пауза STEAM_SWEEP_PAUSE_MS и снова
```

Свойства:
- **Возобновляемость** — прогресс в `sync_state`, рестарт сервера продолжает с той же позиции.
- **Ничего не теряется при 429** — offset не двигается, страница перезапрашивается.
- **Стабильная пагинация** — сортировка по имени; при сортировке по популярности (по умолчанию) позиции переезжают между страницами прямо во время обхода, часть предметов теряется, часть дублируется.
- **Мягкое удаление** — предметы, пропавшие с площадки, помечаются `delisted = 1`, а не удаляются: они могут стоять в составе кейсов.

## Схема

Колонки, добавляемые к `items` (идемпотентно, как `ensureAuthSchema`):

| Колонка | Смысл |
|---|---|
| `price_usd_cents` | исходная цена Steam в центах |
| `rarity_color` | исходный `name_color` Steam |
| `steam_tier` | `Common` / `Uncommon` / `Rare` / `Very Rare` |
| `sell_listings` | сколько лотов на площадке |
| `classid`, `icon_hash` | идентификаторы Steam |
| `delisted` | `1` — предмета больше нет на площадке |
| `last_seen_at` | когда предмет последний раз встретился при обходе |

Плюс индексы по `rarity`, `price`, `delisted` и таблица `sync_state (key, value, updated_at)`.

### Миграция старых редкостей

`normalizeLegacyRarities()` приводит записи от старого синка к палитре сайта. Фронт ([rarity-DBZTLmta.js](../public/assets/js/rarity-DBZTLmta.js)) знает только 5 тиров, а в базе лежали имена из CS:GO, и такие предметы рисовались серыми. Фактически перенесено при первом запуске:

```
CLASSIFIED ->  VIOLET    15 шт.
COMMON     -> REGULAR     2 шт.
COVERT     ->    GOLD     9 шт.
MIL_SPEC   -> UNUSUAL   331 шт.
RESTRICTED ->    RARE   294 шт.
                        651 всего
```

## API

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/v1/skins` | каталог; `?rarity=&minPrice=&maxPrice=&search=&limit=&offset=` (limit ≤ 1000), кэш 30 с |
| GET | `/api/v1/skins/rarities` | сводка по тирам: количество, мин/макс/средняя цена, цвет |
| GET | `/api/v1/skins/status` | прогресс обхода: offset, total, ETA, число 429, курс |
| POST | `/api/v1/admin/sync-skins` | запустить обход; `{"action":"stop"}` — остановить |

```bash
curl -s "http://localhost:3101/api/v1/skins?rarity=GOLD&limit=5"
```

```bash
curl -s http://localhost:3101/api/v1/skins/status
```

## Настройки

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `STEAM_CATALOG_SYNC` | `1` | `0` — не запускать обход |
| `STEAM_REQUEST_INTERVAL_MS` | `3000` | пауза между запросами; **ниже 2000 — риск бана** |
| `STEAM_SWEEP_PAUSE_MS` | `60000` | пауза между кругами |
| `USD_RUB_RATE` | `83` | запасной курс |
| `PRICE_MULTIPLIER` | `1` | наценка магазина |
| `GOLD_MIN_PRICE_RUB` | `5000` | порог тира GOLD, `0` — отключить |

## Что стоит доделать

1. **Приоритетная очередь.** Сейчас все предметы равноправны. Логично чаще обновлять те, что стоят в активных кейсах и в апгрейдере, — им нужна актуальная цена, а редкому дешёвому предмету круга в 27 минут достаточно.
2. **История цен.** `price_usd_cents` перезаписывается. Отдельная таблица снимков дала бы графики и защиту от резких скачков.
3. **Кнопка в админке.** Эндпоинты `/skins/status` и `/admin/sync-skins` готовы, UI для них в админке нет.
