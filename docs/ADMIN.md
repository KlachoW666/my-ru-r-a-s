## Как устроено

### Фабрика CRUD

Полсотни разделов написаны не руками, а через `resource(path, table, fields, opts)`:

```js
resource('/promo', 'promo_codes', ['code', 'kind', 'value', 'uses_limit', 'active'], {
  search: ['code'], filters: { kind: 'kind', active: 'active' }
});
```

Даёт `GET` (с `?search=`, фильтрами, `?page=&limit=`), `GET /:id`, `POST`, `PUT/PATCH /:id`, `DELETE /:id`. В ответе одновременно `data`, `items`, `total` и `pagination` — разные экраны админки читают по-разному.

Для таблиц со строковым идентификатором (`cases`, `telegram`) есть `textIdResource`: `PUT /:id` создаёт запись, если её нет.

### Настройки без своей таблицы

`settings(path, key)` кладёт объект в `app_settings` как JSON. Так работают топ дропов, секретные кейсы, депозитная лестница, настройки кошелька, ботов и стримеров. `PUT` сливает присланные поля с текущими, а не затирает всё.

### Считаемые сводки

Не выдуманные числа, а запросы к реальным таблицам:

| Раздел | Откуда |
|---|---|
| Кошелёк, Бухгалтерия | суммы по `transactions` в разрезе типов; GGR и фактический RTP |
| RTP-дашборд | оборот против выплат, отклонение от заявленного RTP |
| RTP-валидация | ищет кейсы с битым составом и отдачей выше 100% |
| Топ дропов | `battle_drops` с порогом цены из настроек |
| Депозитная лестница | когорты по суммам депозитов из `transactions` |
| Гардиан | счётчики блокировок, правил и забаненных игроков |

### Действия

`POST /invites/generate`, `/guardian/bulk-block`, `/notifications/send`, `/rtp/users` (назначение RTP пачкой), `/kyc/:id/approve|reject`, `/wallet/withdrawals/:id/approve|reject`, `/wallet/skin-deposits/:id/approve|reject`, `/bots/profiles/import`, `/secret-cases/advance`, `/topdrops/recalculate`.

Отклонение вывода **возвращает деньги** игроку и пишет `withdraw_refund` в транзакции. Назначение RTP кладёт итог в `users.rtp` — именно его читает розыгрыш кейсов, так что ползунок реально влияет на выпадение.

## Три ловушки, на которые я наступил

**1. Порядок роутов.** Express берёт первый совпавший обработчик. 32 старые заглушки стояли выше новых и перекрывали их — разделы оставались пустыми даже после того, как настоящие роуты появились. Заглушки удалены.

**2. Литерал против параметра.** `resource('/kyc', …)` объявляет `GET /kyc/:id`, и запрос `/kyc/levels` уходил туда с `id="levels"` → 404. Литеральные пути объявляются **до** параметрических. То же было с `/bots/profiles`.

**3. Неотличимые ответы.** Catch-all отвечал `{success:true, data:[], items:[], total:0}` — байт в байт как пустая таблица. Отладка становилась гаданием. Теперь catch-all добавляет `catchAll: true`.

## Проверка

```bash
curl -s http://localhost:8080/api/v1/admin/config/games
```

Если в ответе есть `"catchAll":true` — обработчика нет, путь нужно добавить в `adminRoutes.js` **выше** catch-all.

Прогон по всем разделам показал: 17 разделов проходят цикл создание → изменение → удаление, 8 кнопок-действий срабатывают, 8 экранов настроек сохраняются.

## Вход

Админка ходит только по passkey (WebAuthn). Первый ключ регистрируется без приглашения, дальше нужен `ADMIN_INVITE_CODE`.

`ADMIN_REQUIRE_AUTH=0` (текущее значение) означает, что **любой запрос проходит без токена**. Перед публикацией на домен: зарегистрировать ключ, затем поставить `1`. `ADMIN_RP_ID` обязан совпадать с доменом в адресной строке — для локальной регистрации `localhost`.

## Что осталось

1. **Прав доступа нет** — любой admin-токен может всё. Ролевой модели (`admin_users.role`) сервер не использует.
2. **Пустые разделы** — KYC, страницы, промокоды, стримеры, модерация скинов, выводы пусты, потому что данных ещё нет. Записи создаются, проверено.
3. **Топ дропов считается только по баттлам** — одиночные открытия кейсов в `battle_drops` не попадают, нужна отдельная таблица дропов.
4. **Промокоды не применяются на сайте** — таблица и админка есть, но `/api/v1/promo/redeem` на игровом сервере всё ещё мок.
