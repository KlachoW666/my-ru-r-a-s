## Как устроено

### Фабрика CRUD

Полсотни разделов написаны не руками, а через `resource(path, table, fields, opts)`:

```js
resource('/promo', 'promo_codes', ['code', 'kind', 'value', 'uses_limit', 'active'], {
  search: ['code'], filters: { kind: 'kind', active: 'active' }
});
```

Даёт `GET` (с `?search=`, фильтрами, `?page=&limit=`), `GET /:id`, `POST`, `PUT/PATCH /:id`, `DELETE /:id`. В ответе одновременно `data`, `items`, `total` и `pagination` — разные экраны админки читают по-разному.

Для таблиц со строковым идентификатором (`cases`, `telegram`) есть `textIdResource`: `PUT /:id` создаёт запись, если её нет.

### Настройки без своей таблицы

`settings(path, key)` кладёт объект в `app_settings` как JSON. Так работают топ дропов, секретные кейсы, депозитная лестница, настройки кошелька, ботов и стримеров. `PUT` сливает присланные поля с текущими, а не затирает всё.

### Считаемые сводки

Не выдуманные числа, а запросы к реальным таблицам:

| Раздел | Откуда |
|---|---|
| Кошелёк, Бухгалтерия | суммы по `transactions` в разрезе типов; GGR и фактический RTP |
| RTP-дашборд | оборот против выплат, отклонение от заявленного RTP |
| RTP-валидация | ищет кейсы с битым составом и отдачей выше 100% |
| Топ дропов | `battle_drops` с порогом цены из настроек |
| Депозитная лестница | когорты по суммам депозитов из `transactions` |
| Гардиан | счётчики блокировок, правил и забаненных игроков |

### Действия

`POST /invites/generate`, `/guardian/bulk-block`, `/notifications/send`, `/rtp/users` (назначение RTP пачкой), `/kyc/:id/approve|reject`, `/wallet/withdrawals/:id/approve|reject`, `/wallet/skin-deposits/:id/approve|reject`, `/bots/profiles/import`, `/secret-cases/advance`, `/topdrops/recalculate`.

Отклонение вывода **возвращает деньги** игроку и пишет `withdraw_refund` в транзакции. Назначение RTP кладёт итог в `users.rtp` — именно его читает розыгрыш кейсов, так что ползунок реально влияет на выпадение.

## Три ловушки, на которые я наступил

**1. Порядок роутов.** Express берёт первый совпавший обработчик. 32 старые заглушки стояли выше новых и перекрывали их — разделы оставались пустыми даже после того, как настоящие роуты появились. Заглушки удалены.

**2. Литерал против параметра.** `resource('/kyc', …)` объявляет `GET /kyc/:id`, и запрос `/kyc/levels` уходил туда с `id="levels"` → 404. Литеральные пути объявляются **до** параметрических. То же было с `/bots/profiles`.

**3. Неотличимые ответы.** Catch-all отвечал `{success:true, data:[], items:[], total:0}` — байт в байт как пустая таблица. Отладка становилась гаданием. Теперь catch-all добавляет `catchAll: true`.

## Проверка

```bash
curl -s http://localhost:8080/api/v1/admin/config/games
```

Если в ответе есть `"catchAll":true` — обработчика нет, путь нужно добавить в `adminRoutes.js` **выше** catch-all.

Прогон по всем разделам показал: 17 разделов проходят цикл создание → изменение → удаление, 8 кнопок-действий срабатывают, 8 экранов настроек сохраняются.

## Вход

Админка ходит только по passkey (WebAuthn). Первый ключ регистрируется без приглашения, дальше нужен `ADMIN_INVITE_CODE`.

`ADMIN_REQUIRE_AUTH=0` (текущее значение) означает, что **любой запрос проходит без токена**. Перед публикацией на домен: зарегистрировать ключ, затем поставить `1`. `ADMIN_RP_ID` обязан совпадать с доменом в адресной строке — для локальной регистрации `localhost`.

Ключ привязывается к строке в `admin_users` и при входе берёт её роль. Чтобы завести ключ не владельцу, а другому администратору, в `POST /auth/register/options` передаётся его `username` вместе с кодом приглашения. Без `username` ключ уходит первому администратору из таблицы — так заводится самый первый ключ.

## Права доступа

Раньше `admin_users.role` существовала, но сервер её не читал: любой действующий токен мог всё — править RTP, подтверждать выводы, заводить других админов.

Теперь запрос раскладывается на **раздел** (первый сегмент пути после `/api/v1/admin`) и **действие** (`read` для GET/HEAD/OPTIONS, `write` для остальных). Раздел относится к домену, роль задаёт уровень доступа к домену. Раскладка живёт в [adminAccess.js](../admin.titanrust.ru/server/adminAccess.js).

Проверка стоит **внутри `requireAdminJWT`**, а не отдельным middleware. Так её нельзя обойти, забыв повесить на новый роут — под защитой оказывается и catch-all.

### Домены

| Домен | Разделы |
|---|---|
| `content` | cases, upgrader, banners, pages, page, media, bots, streamers, giveaways, topdrops, secret-cases, deposit-chain, config |
| `users` | users, kyc, notifications |
| `finance` | wallet, wallet-config, withdrawals, deposits, accounting, transactions, commission-rates, promo |
| `economy` | rtp |
| `security` | guardian, invites |
| `dashboard` | stats |
| `admins` | admins |
| `system` | всё остальное, включая catch-all |

Раздел `auth` открыт любому вошедшему — иначе нельзя было бы даже войти.

### Роли

| Роль | Что может |
|---|---|
| `SUPER_ADMIN` | всё, включая заведение админов и смену ролей |
| `ADMIN` | всё, кроме записи в `admins` (список видит) |
| `FINANCE` | пишет `finance` и `economy`, остальное читает, `admins` не видит |
| `MODERATOR` | пишет `users`, `security`, `content`; деньги только читает, `admins` не видит |
| `VIEWER` | только чтение, `admins` не видит |

Неизвестная роль в токене трактуется как `VIEWER`, а не как владелец: мусор в базе не должен давать прав.

Отказ отвечает 403 и объясняет, чего не хватило:

```json
{"success":false,"code":"FORBIDDEN","message":"Роль «Модератор» может только читать раздел «Финансы»",
 "role":"MODERATOR","section":"wallet","domain":"finance","required":"write","granted":"read"}
```

### Раздел «Администраторы»

`GET|POST /api/v1/admin/admins`, `PUT|PATCH|DELETE /api/v1/admin/admins/:id`, справочник ролей — `GET /api/v1/admin/admins/roles` и `GET /api/v1/admin/auth/roles`. Пароль наружу не отдаётся: колонка осталась от прежнего входа, сейчас вход только по passkey. В списке у каждого админа видно число заведённых ключей.

Два смысловых запрета сверх ролевой проверки: нельзя разжаловать или удалить самого себя и нельзя оставить систему без единого владельца. Вместе с админом удаляются его passkey — иначе по ним можно было бы войти на удалённую учётную запись.

### Роли пользователей сайта

`PATCH /api/v1/admin/users/:id/role` меняет только пользовательские роли `USER`,
`STREAMER` и `CURR_MANAGER`. Операция доступна только `SUPER_ADMIN` и требует
непустое поле `reason` длиной до 500 символов. Изменение роли и запись в
`user_role_history` выполняются в одной SQLite-транзакции. Роли сотрудников
`ADMIN`, `MODERATOR` и другие меняются только в разделе «Администраторы».

### Как проверить роль локально

Заводить passkey ради проверки прав не нужно. При `ADMIN_REQUIRE_AUTH=0` роль берётся из `ADMIN_DEV_ROLE`:

```bash
ADMIN_REQUIRE_AUTH=0 ADMIN_DEV_ROLE=MODERATOR npm run admin
```

По умолчанию `SUPER_ADMIN`, поэтому обычный запуск с выключенной проверкой ведёт себя ровно как раньше.

## Что осталось

1. **Пустые разделы** — KYC, страницы, промокоды, стримеры, модерация скинов, выводы пусты, потому что данных ещё нет. Записи создаются, проверено.
2. **Топ дропов считается только по баттлам** — одиночные открытия кейсов в `battle_drops` не попадают, нужна отдельная таблица дропов.
3. **Ролевая модель не разведена по экранам фронта** — сервер отдаёт `permissions` в `/auth/me`, но бандл админки рисует все пункты меню всем. Запрещённые действия отбиваются на сервере 403-м.
